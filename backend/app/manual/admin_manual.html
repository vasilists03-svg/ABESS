1. Application Overview and Architecture

ABESS is a web application for solving scalar mathematical equations and selecting an appropriate solving method either manually or through the rAIson decision service.

Component Role
Browser frontend Provides authentication, solver controls, graphing, History, My Information and administrator interfaces.
FastAPI backend Handles authentication, API requests, equation validation, method execution, rAIson communication and persistence.
Uvicorn Runs the FastAPI application as the production ASGI server inside the backend container.
SQLite / SQLAlchemy Stores users, guest usage and solve-history information.
nginx Serves the static production frontend.
Caddy Acts as the public reverse proxy and HTTPS entry point for the production domain.
rAIson External decision service used by the Automatic mode to recommend a supported solving method and provide an explanation.
rAIson selects or recommends the method. The actual mathematical computation is performed by the Python backend.

2. Administrator Scope and Application Boundaries

This manual is an operations, maintenance, security and recovery reference for ABESS administrators. It is intentionally separate from the normal User Help.

User-facing method explanations, required numerical inputs, mathematical notation, supported-function examples, rAIson criterion descriptions and equation examples are maintained in the User Help and are not duplicated here.

From an administrator's perspective, the production solver consists of a browser frontend, nginx, a FastAPI/Uvicorn backend, SQLite persistence, the external rAIson decision service and Caddy as the public HTTPS reverse proxy.

The current production application exposes nine supported solving methods. The authoritative user-facing list is kept in the User Help, while implementation and normalization are maintained in app/services/equation_solver.py and app/routers/equation.py.

brentq and fsolve are not public methods of the final production application. Older development or historical database records may still contain legacy names and must not be interpreted as current public functionality.

3. rAIson Integration Administration

rAIson is used for method recommendation in Automatic mode. It does not perform the final mathematical computation. After a supported recommendation has been received and normalized, execution is performed by the ABESS Python backend.

The backend accepts the public ABESS criterion identifiers, converts them to the corresponding rAIson elements internally and normalizes supported rAIson method names to ABESS solver identifiers.

no_context is internal application state. It must not be supplied by an external API caller or exposed as a selectable user option.

Relevant configuration

RAISON_APP_ID RAISON_VERSION RAISON_API_KEY RAISON_TIMEOUT_SECONDS RAISON_METADATA_CACHE_SECONDS

Never display the value of RAISON_API_KEY in logs, documentation, screenshots or support messages.

When Automatic / rAIson fails

  1. Check backend health.
  2. Inspect backend logs.
  3. Confirm that the required rAIson environment-variable names exist without printing their secret values.
  4. Check whether the external rAIson service is reachable.
  5. Inspect the stored selection source, recommendation and explanation in Solve History.
  6. Confirm that a returned recommendation was normalized to a currently supported production method.

4. Accounts, Roles and Administrator Authorization

Protected registered-user and administrator functionality is authenticated with JWT access tokens.

Administrator authorization rule

The backend grants administrator access only after all applicable authentication checks pass.

  1. The JWT must be present and valid.
  2. The referenced user must exist.
  3. The account must be active.
  4. The account must be email-verified.
  5. The account must either have role = "admin" or its email address must match the configured ADMIN_EMAIL.

Failure before authentication normally produces HTTP 401. An authenticated account that does not satisfy administrator requirements normally receives HTTP 403.

Guest access

Guest usage is stored separately from registered-user data. The configured guest limit is enforced by the application and should be inspected through configuration and the Guests view rather than changed directly in production data.

Password recovery and email verification

Verification and password-reset operations depend on the production mail configuration. Password-reset tokens are handled separately from normal JWT access tokens.

5. API Keys, Request Sources and Audit Information

Registered users can have a personal API key for direct API access. API authentication uses the X-API-Key request header.

Never display, log, publish or copy a real personal API key into documentation. Regenerating a user's key invalidates the previous key.

Request source

WEB identifies requests originating from the normal browser application. API identifies requests authenticated through a registered user's personal API key.

Selection source

The request source and the method-selection source are different fields. A request can originate from WEB or API and can independently use Manual or rAIson method selection.

These fields are stored separately so an administrator can diagnose how a request entered the system and how its solver method was selected.

6. Protected Administrator Interfaces

Admin Dashboard

The Admin Dashboard is protected by backend administrator authorization and is intended for application monitoring, usage inspection and review of stored operational data.

Administrator Manual security model

The full operations manual is not stored in the public frontend page. The current architecture is:

Public loader: frontend/admin-help.html Protected manual body: app/manual/admin_manual.html Protected backend endpoint: GET /admin/manual-content Public route through nginx: GET /api/admin/manual-content

The protected endpoint uses get_current_admin. The response is returned with Cache-Control: no-store, private.

The Manual button is displayed in the normal frontend only after the frontend verifies administrator status through the backend.

Expected security behavior

No authentication: GET /api/admin/manual-content Expected: HTTP 401 Authenticated non-admin: Expected: HTTP 403 Authenticated administrator: Expected: HTTP 200 Frontend backup-file URL: Expected: HTTP 404

nginx blocks backup-style files and .vscode paths. The frontend .dockerignore also prevents those files from being copied into new frontend images.

7. Solve History and Diagnostic Result Semantics

Solve History is an operational audit source for both successful and failed requests.

Depending on the request and its result, records can contain the equation, executed method, success state, result or error, iteration count, selection source, request source, rAIson recommendation and rAIson explanation.

Symbolic multi-solution results

When Symbolic Solve produces more than one solution, the top-level root value can represent the first solution used for compatibility with the common solver response shape.

The complete symbolic result can additionally contain:

solutions analytical_solutions numeric_solutions

Administrators diagnosing symbolic requests should inspect the complete solution collections instead of assuming that the single root field represents every solution.

Legacy records

Older rows can contain historical method names, selection values or missing fields that predate the current production schema. Missing historical data must not be reconstructed or invented.

8. User Help Boundary and Incident Diagnosis

The normal User Help is the authoritative source for user-facing mathematical syntax, accepted notation, supported functions, solver inputs, examples and criterion descriptions.

The Administrator Manual should instead be used when the issue concerns deployment, authentication, API access, persistence, method-selection flow, service availability, logging, HTTPS, infrastructure or recovery.

Recommended incident sequence

  1. Confirm that the reported input follows the current User Help.
  2. Check public and internal backend health.
  3. Inspect the corresponding Solve History entry.
  4. Inspect backend logs.
  5. Determine whether the failure belongs to parsing, solver execution, rAIson selection, authentication, database persistence, nginx or Caddy.
  6. Reproduce only with non-secret test data before modifying production code or configuration.

Create a consistent SQLite backup:

docker exec equation-solver-backend python -c "import sqlite3; s=sqlite3.connect('/data/app.db'); d=sqlite3.connect('/tmp/app_backup.db'); s.backup(d); d.close(); s.close()"

Then run the database integrity check and backend health check.

18. Admin Dashboard

The Admin Dashboard provides a summary of application activity together with registered-user, solve-history and guest-usage information.

The dashboard is read-only. It is intended for monitoring application usage and reviewing recorded activity. It does not display user passwords or personal API keys.

Overview statistics

Item Meaning
Registered Users Number of registered user accounts stored by the application.
Total Attempts Total number of recorded equation-solving attempts. This includes both successful and failed attempts.
Successful Recorded attempts that produced a valid solver result.
Failed Recorded attempts that did not produce a valid solver result.
Manual Attempts where the solving method was selected directly by the user.
rAIson Attempts where method selection was performed through the Automatic / rAIson flow.
Web Requests Recorded attempts originating from the normal web-application flow.
API Requests Recorded attempts authenticated with a registered user's personal API key.
Guest Users Number of guest-usage records created by the application.
Guest Attempts Total number of solver uses recorded for guest sessions.
Verified Users Registered users whose email address has been successfully verified.

Users tab

The Users tab lists the registered accounts known to the application.

  • ID: internal database identifier of the account.
  • Email: registered email address.
  • Role: normally user or admin.
  • Verified: indicates whether email verification has been completed.
  • Active: indicates whether the account is currently enabled.
  • Created: account creation date and time.

Solve History tab

Solve History contains the recorded solving attempts, including both successful and failed attempts.

Column Meaning
User Registered-user email when available, otherwise the corresponding guest identifier.
Equation Equation or expression submitted to the solver.
Method Solver method associated with the recorded attempt.
Status Success means that a valid result was produced. Failed means that the attempt ended without a valid result.
Result / Error Shows the result for a successful attempt. For a failed attempt, the stored error code and user-readable error message are shown when available.
Selection Manual means the method was selected directly by the user. rAIson means the method was selected through the Automatic / rAIson flow.
Request WEB indicates the normal web-application flow. API indicates a request authenticated with a personal API key.
Date Date and time at which the attempt was recorded.
Older database records may contain legacy values such as automatic_fallback or may not contain the newer status or request-source information. These records are preserved as historical data.

Guests tab

The Guests tab summarizes usage performed without a registered account.

  • Guest ID: anonymous identifier assigned to the guest session.
  • Attempts: number of solver uses recorded for that guest.
  • Created: time at which the guest-usage record was created.
  • Last Used: most recent recorded use of that guest identifier.

Refresh

Use the Refresh button to request the latest statistics, users, solve history and guest data from the backend.

20. Login, JWT and SECRET_KEY

User and administrator sessions use JWT access tokens.

If a token expires or becomes invalid, log in again.

Never place the SECRET_KEY in documentation, screenshots, Git repositories, messages, or public files.

27. Caddy, HTTPS, TLS and Reverse Proxy Operations

Current ABESS TLS configuration

The current production configuration uses an explicit certificate and private key rather than Caddy-managed automatic HTTPS.

abess.hmu.gr { tls /etc/caddy/certs/abess-fullchain.pem /etc/caddy/certs/abess-private.key reverse_proxy frontend:80 }

The host-side directory ~/ABESS_LOCAL/backend/certs is mounted read-only inside the Caddy container as /etc/caddy/certs.

Host: certs/abess-fullchain.pem certs/abess-private.key Container: /etc/caddy/certs/abess-fullchain.pem /etc/caddy/certs/abess-private.key

The current expected host permissions are:

abess-fullchain.pem : 0644 abess-private.key : 0600
The private key must never be displayed, copied into documentation, committed to Git or sent through messages.

At the time this manual was updated, the deployed certificate was issued by HARICA for abess.hmu.gr and was valid until 11 April 2027. Always verify the live certificate before maintenance because certificate metadata changes after renewal.

Current ABESS certificate replacement procedure

Because the current production Caddyfile references fixed filenames, a normal certificate renewal can keep the same filenames and replace their contents on the host.

  1. Confirm that the replacement full-chain certificate and private key are the intended files.
  2. Verify certificate metadata and confirm that the certificate and key belong to the same key pair.
  3. Back up the two active TLS files locally on the server.
  4. Replace the active host-side files while keeping the same production filenames.
  5. Restore the expected permissions and verify ownership.
  6. Validate the Caddy configuration before restart.
  7. Restart Caddy and verify the public certificate, website and API health endpoint.

Back up the currently active ABESS certificate

Keep certificate backups outside the active certs/ directory. Private-key backups must remain on the server with restricted permissions.

cd ~/ABESS_LOCAL/backend mkdir -p backups/tls chmod 700 backups/tls stamp=$(date +%F_%H%M%S) cp certs/abess-fullchain.pem \ "backups/tls/abess-fullchain.pem.$stamp" cp certs/abess-private.key \ "backups/tls/abess-private.key.$stamp" chmod 600 \ "backups/tls/abess-private.key.$stamp" ls -l backups/tls

Install a replacement using the existing production filenames

cp NEW_FULLCHAIN.pem certs/abess-fullchain.pem cp NEW_PRIVATE_KEY.key certs/abess-private.key chmod 644 certs/abess-fullchain.pem chmod 600 certs/abess-private.key ls -l certs/abess-fullchain.pem certs/abess-private.key
NEW_FULLCHAIN.pem and NEW_PRIVATE_KEY.key are placeholders. Replace them with the real new files only after validating them. Preserve the current ownership unless there is a deliberate administrative reason to change it.

Determine how TLS is currently managed

Do not assume that the server uses manually installed certificate files. First inspect the active Caddy configuration.

docker inspect equation-solver-caddy --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}' docker exec equation-solver-caddy caddy adapt --config /etc/caddy/Caddyfile --pretty

If the Caddy configuration uses normal automatic HTTPS without an explicit certificate/key pair, Caddy manages certificate issuance and renewal itself. In that case, do not manually replace files inside Caddy's certificate storage. Investigate DNS, CAA, network access, persistent Caddy storage and Caddy logs if renewal fails.

If the Caddyfile contains an explicit TLS certificate and private-key configuration, follow the manual certificate-replacement procedure below.

Manual certificate replacement - preparation

  1. Confirm the production directory and running containers.
  2. Identify the host-side Caddyfile and any mounted certificate directories with docker inspect.
  3. Record the exact certificate, full-chain and private-key paths currently referenced by Caddy. Do not guess filenames.
  4. Create server-local backups before changing any file. Keep private-key backups on the server and protect them with the same or stricter permissions.
  5. Inspect the new certificate validity, subject and issuer before installation.
  6. Confirm that the new certificate and private key belong to the same key pair.

Inspect a new certificate before installation

openssl x509 -in NEW_CERTIFICATE.pem -noout -subject -issuer -dates -serial

Verify that certificate and private key match

The following two commands should produce the same SHA-256 value. Run them only on the server. Do not copy the private key into messages or documentation.

openssl x509 -in NEW_CERTIFICATE.pem -pubkey -noout | openssl pkey -pubin -outform DER | sha256sum openssl pkey -in NEW_PRIVATE_KEY.key -pubout -outform DER | sha256sum

Back up current TLS configuration and files

Replace the placeholders below only after identifying the real host-side paths. A private-key backup must stay on the server.

cp CADDYFILE_PATH CADDYFILE_PATH.bak_$(date +%F_%H%M%S) cp CURRENT_CERTIFICATE_PATH CURRENT_CERTIFICATE_PATH.bak_$(date +%F_%H%M%S) cp CURRENT_FULLCHAIN_PATH CURRENT_FULLCHAIN_PATH.bak_$(date +%F_%H%M%S) cp CURRENT_PRIVATE_KEY_PATH CURRENT_PRIVATE_KEY_PATH.bak_$(date +%F_%H%M%S)
The names above are placeholders, not commands to run literally. First inspect the actual mounted paths and active Caddy configuration.

Install the replacement certificate

Replace only the files or Caddy TLS paths confirmed in the active configuration. Preserve appropriate ownership and permissions. In particular, do not make the private key world-readable.

stat CURRENT_CERTIFICATE_PATH stat CURRENT_FULLCHAIN_PATH stat CURRENT_PRIVATE_KEY_PATH

After installing the new files, inspect their ownership and permissions again before restarting Caddy.

Validate Caddy before restart

docker exec equation-solver-caddy caddy validate --config /etc/caddy/Caddyfile
Do not restart Caddy when configuration validation fails. Correct the configuration or restore the previous files first.

Activate and verify the replacement

docker compose -f docker-compose.production.yml restart caddy docker logs --tail 100 equation-solver-caddy curl -I https://abess.hmu.gr curl -i https://abess.hmu.gr/api/health openssl s_client -connect abess.hmu.gr:443 -servername abess.hmu.gr </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates -serial

Verify that the certificate shown by the public HTTPS endpoint is the intended replacement and that both the main site and API health endpoint continue to respond correctly.

Certificate rollback

If HTTPS fails after a manual replacement, restore the previously verified Caddy configuration and TLS files from their server-local backups, validate the Caddyfile, restart Caddy and repeat the public HTTPS checks.

cp CADDYFILE_BACKUP CADDYFILE_PATH cp CERTIFICATE_BACKUP CURRENT_CERTIFICATE_PATH cp FULLCHAIN_BACKUP CURRENT_FULLCHAIN_PATH cp PRIVATE_KEY_BACKUP CURRENT_PRIVATE_KEY_PATH docker exec equation-solver-caddy caddy validate --config /etc/caddy/Caddyfile docker compose -f docker-compose.production.yml restart caddy docker logs --tail 100 equation-solver-caddy curl -I https://abess.hmu.gr curl -i https://abess.hmu.gr/api/health
The rollback filenames above are placeholders. Use only backups that were created and verified before the failed change.

Automatic HTTPS renewal troubleshooting

When Caddy manages HTTPS automatically, investigate certificate-renewal problems without manually editing Caddy's internal certificate storage.

date dig A abess.hmu.gr +short dig AAAA abess.hmu.gr +short dig CAA abess.hmu.gr +short docker logs --tail 200 equation-solver-caddy docker inspect equation-solver-caddy --format '{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'

Confirm that DNS resolves to the expected server, current CAA policy permits the intended certificate authority, ports 80/443 and the required network path are available, server time is correct and persistent Caddy storage has not been removed.

Remote Desktop

systemctl status xrdp

Logging out of the Linux desktop or terminal

Verify the state after reconnecting:

docker compose -f docker-compose.production.yml ps

After a server reboot

systemctl is-active docker docker compose -f docker-compose.production.yml ps curl -i https://abess.hmu.gr/api/health

If Docker is not running:

sudo systemctl start docker
Reboot the production host only during intentional maintenance and only when remote access is known to be recoverable.

30. Rollback and Recovery

Source rollback must use a verified known-good backup or production freeze. Database rollback is a separate operation and must use a verified SQLite backup.

Current release freeze

/home/rosinante/ABESS_LOCAL/backups/production_freeze_20261005
Never overwrite an existing production freeze. A freeze is a historical recovery point and must remain immutable after verification.

The previous production_freeze_20261004 is also historical and must never be replaced or modified.

Rollback procedure

  1. Identify which source or configuration file caused the regression.
  2. Confirm that the selected production freeze contains the expected known-good copy.
  3. Back up the currently deployed broken file before replacing it.
  4. Restore only the affected file or files from the freeze.
  5. Run Python, nginx or Caddy validation as applicable.
  6. Rebuild only the affected Docker service whenever possible.
  7. Run health, security and regression checks again.

Database recovery

Do not restore application source backups into /data/app.db. Restore the production database only through the dedicated database procedure using a backup that has passed PRAGMA integrity_check.

Never use a database restore simply to test whether a backup is valid. Verify the backup separately first.

31. Final Production Verification Checklist

After a significant production change, run all checks that are relevant to the affected component.

  1. Docker service is active.
  2. Backend, frontend and Caddy containers are running.
  3. Modified Python files pass syntax validation.
  4. nginx configuration passes nginx -t.
  5. Caddy configuration validates if Caddy was modified.
  6. Public https://abess.hmu.gr/api/health returns HTTP 200.
  7. Internal backend /health returns HTTP 200.
  8. The main website opens through HTTPS.
  9. Registration, verification, login and password reset work when authentication code or email configuration changed.
  10. Manual equation solving works when solver code changed.
  11. Automatic / rAIson solving works when selection or rAIson code changed.
  12. Successful and failed attempts are recorded correctly in Solve History.
  13. WEB/API request source and Manual/rAIson selection source are recorded correctly when related code changed.
  14. Personal API-key authentication works when API-key code changed.
  15. Admin Dashboard loads statistics, users, Method Usage, Solve History and guest information.
  16. Admin users can see the Manual button.
  17. Guest and normal non-admin users cannot see the Manual button.
  18. Unauthenticated /api/admin/manual-content returns HTTP 401.
  19. An authenticated non-admin request to the protected Manual endpoint returns HTTP 403.
  20. An authenticated administrator can load the complete protected Manual.
  21. Public requests for frontend backup files return HTTP 404.
  22. Guest-limit behavior remains correct when guest code or configuration changed.
  23. Graph rendering works when graph/frontend solver code changed.
  24. Database integrity check returns ok.
  25. Production logs contain no unexpected repeated errors.
  26. Browser cache is refreshed after frontend changes.

When all checks relevant to the change pass, the production application can be considered ready for normal use.

32. Important Safety Rules

  • Never use docker compose down -v on the production system.
  • Never replace /data/app.db with backend/app.db.
  • Always create and verify a database backup before restoring data.
  • Never publish .env.
  • Never expose passwords, JWT tokens, API keys, SECRET_KEY, or TLS private keys.
  • After source-code changes, rebuild the appropriate Docker image.
  • After a server reboot, confirm that all production containers are running.
